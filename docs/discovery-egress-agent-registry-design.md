# Discovery egress and agent registry: fail-closed cutover

Baseline: `7bde921` (`origin/main`, 2026-10-07). Founder Choice C: no private/internal discovery for **any** role; no allowlist, admin exception, or unverified platform-admin authority. A separately reviewed P-6 dedicated platform-admin identity plus org-specific allowlist is required before private/internal discovery can become available.

## Schema and migration ownership

`discovery_agents` in `001_complete_schema.sql` has globally unique `agent_id` but no `organization_id`. Add a nullable UUID `organization_id` with no default and an index on `(organization_id, last_heartbeat_at DESC)` in a new forward migration. Existing rows remain NULL and cannot be read, selected, updated, deleted, or reused by any caller. All new registrations insert the verified caller organization; the global unique `agent_id` stays global. On conflict update only when `discovery_agents.organization_id = EXCLUDED.organization_id`, using `RETURNING` to distinguish rejected collisions without disclosing whether the ID exists. Heartbeat/delete similarly filter by both ID and organization, returning the same 404 for foreign, NULL and missing IDs. List/get/find-best require the verified organization and never include NULL. The scheduled stale-status update is internal maintenance, not an agent lookup. `001`'s public grants on the table and two unscoped legacy views (`active_discovery_agents`, `agent_network_coverage`) are revoked in this migration; there are no API consumers of those views. Application DB ownership still requires API query scoping; this is not row-level security for arbitrary SQL by that owner.

Migration collision inventory at this baseline: `origin/main` at `7bde921` contains PostgreSQL migrations through `010_business_service_views_org_functions.sql`; the unmerged `ao/cmdb-73-pr42` HP1 branch has `011_ci_organization_scope.sql`, while unmerged `ao/cmdb-97` R-CRED-2 has `018_connector_organization_scope.sql`/F2. No branch has a conflicting 019 at this inspection. `019_discovery_agents_organization_scope.sql` is a **provisional** standalone filename, not a dependency on either pending branch: `migrator.ts` discovers direct `.sql` files, sorts them lexicographically and tracks exact filenames with SHA-256 checksums; it imposes no contiguous-number requirement. This migration only references `001`'s agent table and views, so it runs on 001-010 alone or after 011/018 when merged. Re-inventory actual merged filenames immediately before PR/head; rename this *unapplied* migration if 019 conflicts. Never rename/modify an applied migration or reuse a checksum. Do not run against a real database as part of this slice. No automatic rollback is offered: dropping the column destroys ownership and restoring old unscoped binaries reopens cross-org access. Older binaries must not run after this migration because they write inaccessible NULL rows. No allowlist schema is introduced.

## Egress boundary

Discovery protocol and AI-tool entrypoints (discovery-engine nmap/SSH/AD, ai-discovery nmap/SSH/HTTP probe, and pattern HTTP fetch) refuse prohibited hostnames and resolved addresses before outbound scans. Nmap receives only canonical pinned IPs or validated CIDRs with no forbidden overlap; a mixed batch fails before starting any scan. Arbitrary ranges, lists, target options or unresolved hostnames are never passed to a subprocess. The AI nmap tool invokes `execFile`, not a shell; arbitrary NSE scripts and aggressive scripting/traceroute are refused because their secondary egress cannot be checked. SSH resolves every address and pins an allowed address in the connect configuration, with a second lookup immediately before connecting. HTTP probe and patterns use a pinned socket DNS lookup, disallow proxies, and never follow redirects; future redirect support must separately revalidate every hop. LDAP uses a pinned checked numeric endpoint and retains the original hostname for TLS verification. New adapters must use the policy at the actual outbound boundary; those without connect-time address pinning must refuse. All policy refusal errors are the same constant and contain no target.

## Pattern operator cutover

The compiler now stores strict `detection-v1` and `discovery-v1` JSON plans in the existing `detection_code` and `discovery_code` columns; no stored JavaScript is evaluated. Plans retain port/header/endpoint/service-name scoring and fixed metadata/HTTP endpoint discovery. Endpoint paths are restricted to safe relative paths and HTTP requests still use the pinned discovery transport. Previously stored JavaScript patterns are **not** converted automatically: validation rejects them, and both matching and direct execution surface `UNSUPPORTED_PATTERN_PLAN` without running them. Hybrid discovery returns this explicit error rather than silently falling back to AI. Operators must deactivate old executable patterns and recompile from reviewed sessions into declarative plans before reactivation. Legacy pattern availability is reduced until then; manual fallback is an explicitly authorized new discovery request, not an implicit bypass.
