# Build01 staging

The live staging Compose project is staging-happycmdb, managed by the portfolio `deploy-app.sh` with a per-generation volume override. The deployer supplies IMAGE_TAG as a full commit SHA (Compose defaults to local without it).

## Services

| Service | Purpose | Published port |
| --- | --- | --- |
| api-server | REST and GraphQL API | 127.0.0.1:${HAPPYCMDB_API_PORT:-19000} → 3000 |
| web-ui | Nginx React UI, proxies API/GraphQL | 127.0.0.1:${HAPPYCMDB_WEB_PORT:-19080} → 80 |
| postgres | TimescaleDB/PostgreSQL | internal only |
| migrator (profile `migrate`) | One-shot schema migration using the api-server image, as the owner login; opt-in only | internal only |
| app-login (profile `migrate`) | One-shot, as the owner login: creates or re-asserts the API login `cmdb_app` before every migrator run | internal only |
| neo4j | Graph database | internal only |
| redis | Cache and BullMQ queue | internal only |

Kafka is optional and intentionally omitted, along with Zookeeper, test SSH, Grafana, Metabase, and Kafka UI. Published ports are loopback-only behind the host proxy.

## Client address for rate limits (HAP-1091)

The API keys every rate limit on `req.ip`, taken `TRUST_PROXY` hops back in X-Forwarded-For. Staging defaults to `${HAPPYCMDB_TRUST_PROXY:-2}` (operator ruling `approvals/operator-ruling-cmdb-hap1091-staging-trust-proxy-20261108T085406Z.go`). Chain: tailnet client → tailscale serve `:8449` (tailnet only; overwrites X-Forwarded-For with the peer address) → `127.0.0.1:19080` docker-proxy → web-ui nginx (appends its remote_addr, the bridge gateway 172.23.0.1) → api, which receives `<peer>, 172.23.0.1`. Two hops back is the tailnet peer, which a tailnet client cannot forge; one hop would put every staging user on 172.23.0.1.

If the `:8449` serve mapping is removed, staging is loopback-only: set HAPPYCMDB_TRUST_PROXY=1.

Accepted residual (LOW, host-local only): a process on Build01 calling `127.0.0.1:19080` directly can forge one hop, and one calling `127.0.0.1:19000` (the API publish) can send any X-Forwarded-For, so either can choose its own rate-limit key.

## Environment variable names

Required secret/config names (Infisical /staging path /happycmdb):
- JWT_SECRET — JWT signing secret.
- JWT_ISSUER — required issuer stamped and verified on JWTs.
- JWT_AUDIENCE — required audience stamped and verified on JWTs.
- ENCRYPTION_KEY — credential encryption key consumed as CREDENTIAL_ENCRYPTION_KEY.
- NEO4J_PASSWORD — Neo4j user password.
- POSTGRES_PASSWORD — password of the PostgreSQL owner login `cmdb_user` (migrator, app-login, rollback).
- POSTGRES_APP_PASSWORD — password of the API login `cmdb_app`; random, at least 32 characters, generated on Build01 (HAP-1562).
- STAGING_PUBLIC_URL — staging UI origin/hostname used to constrain allowed origins.
- AUDIT_CHAIN_KEY — audit hash-chain HMAC key (32-byte hex); journaled CI writes fail closed (503) without it; never rotate without a re-chain plan.

Optional names: POSTGRES_APP_USER (the API's PostgreSQL login; defaults `cmdb_app`, set to `cmdb_user` only to roll back, see below), REDIS_PASSWORD (only when Redis auth enabled), IMAGE_TAG (defaults local), HAPPYCMDB_API_PORT (defaults 19000), HAPPYCMDB_WEB_PORT (defaults 19080), METRICS_SCRAPE_TOKEN (bearer token for root `/metrics`, at least 32 characters; unset or shorter answers 404). NODE_ENV, database hosts/ports, Kafka brokers, JWT expiration, and internal TLS settings are fixed. See [production parity](PRODUCTION-PARITY.md). Never commit secret values.

## PostgreSQL logins (HAP-1562)

- `cmdb_user` is the owner login (the image's bootstrap superuser, owner of every table). Only the migrator and app-login use it.
- `cmdb_app` is the API login: NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS, owns nothing. Its privileges come from migration 045 (`045_staging_app_login_acl.sql`): the tables, columns and sequences the API reads and writes, including the reconciliation journal and `ci_reconciliation_epochs`; and from the migrations that grant it their own table (046 `service_offerings`, 047 `ai_sync_cursors`, 048 `portfolio_imports`/`portfolio_import_map`, 054 `relationship_evidence_receipts`, 056 `estate_kpi_snapshots`). It cannot run DDL.
- Order: `--profile migrate run --rm migrator` first runs app-login (Compose `depends_on`), which creates `cmdb_app` with POSTGRES_APP_PASSWORD, so the role exists before 045 grants it and before the API cuts over. app-login re-applies 045 and the per-table grants of 046, 047, 048, 054 and 056 (the `$hap2126$` block of `build01-staging-app-login.sql`) when 045 is already recorded, so a re-created `cmdb_app` equals a freshly migrated one (the PGlite test `staging-app-login-receipts-grant.test.ts` pins the listed tables, and the `Staging Migration Contract` job re-creates the role and diffs its whole grant matrix). A new table that a migration grants `cmdb_app` MUST be added to the `$hap2126$` list. The guard is the hosted `Staging Migration Contract` job (`test-staging-migrations.sh`), whose full-set grant-matrix diff fails when it is not; the PGlite matrix test is not a guard for a future 057+ grant, because its `TABLE_MIGRATIONS` list is hard-coded (046, 047, 048, 054, 056). The password never appears in output or the server log.
- Done-when probe (read-only; one SELECT in a READ ONLY transaction, rolled back), with the same `-p`/`-f` arguments the deployer uses for the project:
  `docker compose -p <project> -f deploy/build01-staging.compose.yml -f <generation override> exec -T api-server node - < deploy/api-db-role-probe.cjs`
  It prints `current_user=cmdb_app rolsuper=false` and exits 0; it exits 2 when the API runs as a superuser and 1 when the probe cannot connect. It never prints a password.
- Startup check (HAP-1575): after the logging banner and before it loads connectors or listens, the API runs the same one-statement probe on its own login (`BEGIN READ ONLY`, a 5 s `SET LOCAL statement_timeout`, `SET LOCAL search_path = pg_catalog, pg_temp` (the probe reads `pg_roles`, `pg_has_role` and other catalog names unqualified, so a `search_path` set on the login, plus CREATE on a schema in it, could otherwise resolve them to objects the login created and report all clear; `pg_temp` is last so temp objects cannot shadow either), `SHOW server_version_num`, the one probe `SELECT` built for that server version (a bare `system_user` is not a keyword before PostgreSQL 16 and fails there with SQLSTATE 42703, undefined column, so only 16+ gets it), `ROLLBACK`; `deploy/api-db-role-probe.cjs` stays the operator tool, pins the same `search_path` and still tests `current_user` only). The probe reads `current_user` and `session_user` and flags eight things: `rolsuper` and `rolbypassrls` of `current_user` (neither attribute is inherited through role membership), `session_user_privileged` (the session login, before any `SET ROLE`, is a superuser or has BYPASSRLS), and `can_set_privileged_role` (`current_user` or `session_user` is a direct or indirect member of another superuser or BYPASSRLS role, inherited or not, so it can `SET ROLE` to it; a `NOINHERIT` membership still allows `SET ROLE`, so it is flagged on purpose), `session_authorization_masked` (PostgreSQL 16+: `session_user` differs from the authenticated login, `system_user` without its `method:` prefix, so a superuser login used `SET SESSION AUTHORIZATION` to look like another role; methods that map the identity, such as `peer` or `cert`, can report an identity that differs from the role name and are flagged too), `dangerous_builtin_role_member` (`current_user` or `session_user` is a direct or indirect member of `pg_execute_server_program`, `pg_write_server_files`, `pg_read_server_files`, `pg_read_all_data` or `pg_write_all_data`, whichever exist on the server, whatever the `INHERIT`, `SET` or `ADMIN` options of the grant), `createrole_escalation` (PostgreSQL 15 or older: `current_user` or `session_user` is a direct or indirect member of a `CREATEROLE` role, itself included, so it holds or can `SET ROLE` to a role that can grant itself any role, `pg_execute_server_program` included; on 16+ `CREATEROLE` alone no longer grants roles the creator does not hold, so it is not flagged), and `replication_escalation` (`current_user` or `session_user` is a direct or indirect member of a role with `REPLICATION`, itself included, so it holds or can `SET ROLE` to a role that has the attribute; the attribute is not inherited, but a member can `SET ROLE` to the holder). What the attribute reaches depends on how the login got it: a walsender (`pg_basebackup`, the replication protocol) checks `REPLICATION` on the authenticated login at connect time, so a member that only gets the attribute through `SET ROLE` gets the SQL slot functions (`pg_create_logical_replication_slot`, `pg_logical_slot_get_changes`), which need `wal_level=logical` and return only changes made after the slot exists; only a login that holds `REPLICATION` itself gets a base backup or the replication protocol (subject to the `replication` entries of `pg_hba.conf`). The flag is correct either way. On PostgreSQL 16+ a `REPLICATION` membership granted `WITH SET FALSE, INHERIT FALSE` confers no access by itself, but a holder of `ADMIN OPTION` on that role can re-grant it to itself `WITH SET TRUE` and then `SET ROLE` to it (observed on PostgreSQL 18.3): the flag stays raised, a deliberate conservative false positive without `ADMIN OPTION` that fails safe. A login with none of the eight logs one `info` line with `current_user`, `session_user` and the eight flags. Any one of them logs an `error` line with the same fields and the API keeps starting. A superuser ignores row level security and every grant check; a BYPASSRLS role ignores row level security policies only, its grants still apply. A superuser is a member of every role, so it also reports `can_set_privileged_role=true`, and `replication_escalation=true` when some role in the cluster has `REPLICATION` (the flag is `pg_has_role` against the roles holding the attribute; the bootstrap superuser normally has it); `rolsuper` flags the superuser either way. `pg_read_all_data` and `pg_write_all_data` are flagged because they skip the table grant checks for reads and for writes on every table, which voids the least-privilege grants of the app login; neither bypasses row level security. Not covered: object ownership (inherited ownership through `pg_database_owner` or an owner role is not inspected); `CREATEDB` is deliberately unflagged (no known escalation: cloning a non-template database needs ownership or superuser); these predefined roles are deliberately unflagged (none of them DIRECTLY breaks the tenant boundary, and flagging them would be advisory noise that trains operators to ignore the error line); `pg_read_all_settings` (and `pg_monitor`, which contains it) can break it INDIRECTLY where a setting holds a credential, for example `primary_conninfo` on a standby, so the app login should hold none of these roles; the guard does not check them, they are advisory residuals an operator should review (operator check: `SELECT pg_has_role('cmdb_app', 'pg_read_all_settings', 'MEMBER')` should return `f`, and it also covers indirect membership through `pg_monitor`; `build01-staging-app-login.sql` refuses any membership row for `cmdb_app` when it (re)creates the login, and this operator check is what detects a grant made out of band afterwards): `pg_monitor` and `pg_read_all_stats` read other sessions' query text in `pg_stat_activity` and `pg_stat_statements`, `pg_read_all_settings` (also part of `pg_monitor`) shows settings that are otherwise superuser-only: depending on the server version and the deployment these can include command lines (`ssl_passphrase_command`, and `archive_command` and `restore_command` where the server hides them from other roles) and connection strings (`primary_conninfo`) that can carry credentials, `pg_signal_backend` can cancel or terminate other non-superuser backends (a denial of service), `pg_create_subscription` (16+), with `CREATE` on the database, lets the member create a subscription that connects from the database server to a host of its choosing: a server-side outbound-connection (SSRF-style) primitive from the database host, `pg_maintain` (17+) runs `LOCK`, `VACUUM`, `REINDEX` and `REFRESH` on every relation (a denial of service), `pg_checkpoint` (15+) runs `CHECKPOINT`, and `pg_use_reserved_connections` (16+) uses the connection slots reserved by `reserved_connections`; on PostgreSQL 15 and older `session_authorization_masked` is always `false` because `system_user` does not exist there (a limitation, not an all clear), and it is also `false` when `system_user` is NULL (`trust`: no authenticated identity to compare); capabilities granted by an extension or by object privileges (for example `EXECUTE` on an extension function that reads files) are not inspected. The Build01 staging provisioning (`build01-staging-app-login.sql`) already refuses any `pg_auth_members` row for `cmdb_app` and asserts `NOCREATEROLE`, and `cmdb_app` is `NOREPLICATION`, so none of these flags is set for it. If the probe itself fails (cannot connect, role row missing) the API logs a `warn` with the SQLSTATE only and keeps starting. No log line or error carries a password, connection string or the database's error message.
- `REQUIRE_NON_SUPERUSER_DB` (compose default `false`): only the string `true` (case-insensitive, surrounding whitespace ignored) enables enforcement; any other value, including `1`, `yes` and empty, leaves it off. With `true` the API throws from startup and exits non-zero before it listens when any check above flags the login (it is or can become a superuser or BYPASSRLS role, or holds an escalation capability listed above), and also when the probe fails (fail closed). The check runs once at startup, not per request.
- A new API-side table or query needs a grant to `cmdb_app` in its migration; the `hap1562-real-store` CI job runs the API's queries as `cmdb_app`.
- Prerequisites before deploying this change: POSTGRES_APP_PASSWORD exists for the project (every Compose command refuses to start without it) and the target generation is migrated (`cmdb.schema_migrations` exists), so app-login and 045 run. An init-built generation without the ledger (g15) is never migrated (below) and has no `cmdb_app`: run it with the rollback settings, never with the default `cmdb_app`.

**Rollback to `cmdb_user`** (under the staging-happycmdb lock): set POSTGRES_APP_USER=`cmdb_user` and POSTGRES_APP_PASSWORD to the POSTGRES_PASSWORD value for the project, then recreate only the API: `docker compose -p <project> -f deploy/build01-staging.compose.yml -f <generation override> up -d --no-deps api-server`. The probe then prints `current_user=cmdb_user rolsuper=true` (exit 2, expected after a rollback). In this mode app-login does nothing and the migrator still runs as `cmdb_user`. To return to `cmdb_app`, unset POSTGRES_APP_USER and restore the generated POSTGRES_APP_PASSWORD; app-login refuses the owner password for `cmdb_app`. Retiring `cmdb_app` is optional and only after no session uses it: `045_staging_app_login_acl.down.sql` (refuses while a `cmdb_app` session is open) revokes every `cmdb_app` privilege, sets the role NOLOGIN and un-records 045-048; removing the role is then `DROP OWNED BY cmdb_app; DROP ROLE cmdb_app;` as `cmdb_user`. After that script, returning to `cmdb_app` needs no manual `ALTER ROLE`: app-login re-asserts LOGIN and the migrator re-applies 045-048. `deploy/test-staging-migrations.sh` exercises the API rollback and the generation-94 upgrade (ledger without 045 and without `cmdb_app`) in CI.

With `POSTGRES_APP_USER=cmdb_user` the startup check logs the `error` line on every API start (expected while the rollback is in use). `REQUIRE_NON_SUPERUSER_DB` MUST be unset or `false` while the rollback setting is in use: with `true` the API refuses to start as `cmdb_user`. Set it to `true` only after returning to `cmdb_app`.

## Storage and startup

Named data volumes: neo4j_data, neo4j_logs, neo4j_plugins, postgres_data, redis_data. The bare Compose file declares project-scoped volumes, but the deployer binds live and candidate stacks to external `staging-happycmdb-data-g<N>_*` volumes using `/home/nzitzer/.staging-overrides/happycmdb-g<N>.yml`. At this finding the existing init-postgres-built live Postgres volume is `staging-happycmdb-data-g15_postgres_data`; a fresh candidate would use the next generation, not the live volume or the bare file's `staging-happycmdb_postgres_data`. NEVER use the bare Compose file against the live project: it omits that generation binding and can target the wrong volume or disrupt the live Postgres service. Removing the initdb mount does not change any existing volume.

**Migration safety prerequisite:** Only a fresh NEXT-generation candidate `postgres_data` volume may receive canonical migrations, after a verified backup of the live-generation volume and founder approval. Before any migration, the operator must verify that the resolved volume binding is the fresh candidate generation, not the existing init-postgres-built g15 live volume or a bare-Compose project volume. NEVER migrate the current live generation: it has no `cmdb.schema_migrations`, and migration SQL can partially succeed against its pre-existing schema. This runbook does not authorize migration, volume rebuilding, or host deployment.

A fresh Postgres volume no longer runs staging initdb SQL and needs canonical SQL migrations before API traffic. Default unqualified Compose `up -d` does not start the opt-in-profile migrator. The founder-approved route is a separate portfolio `deploy-app.sh` change: its one-time `STAGING_FRESH_VOLUMES=postgres_data` opt-in creates only the next-generation Postgres volume empty while other data volumes are copied with data services stopped; it runs the migrator on the candidate with the generation override before cutover, never on the live project. Approval of that route does not mean the host script is merged, installed, or authorized to run a rebuild window. The migrator uses `/app/packages/database/src/postgres/migrations` in the candidate's full-SHA image, records checksums in `cmdb.schema_migrations`, and exits nonzero on migration failure. Health checks do not confirm migration completion. Confirm API at http://127.0.0.1:19000/api/v1/cmdb-health and UI at http://127.0.0.1:19080/.
